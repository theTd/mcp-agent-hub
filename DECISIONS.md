# Decisions

Design decisions confirmed by the owner. Change a line here before changing the behaviour it records.

## Rust terminal core (2026-11-12, owner: decision page `hub-rust-core-1112`)

Design: `docs/rust-terminal-core.md`. On `feat/rust-terminal-core`: step 0 (frozen corpus), step 1 (ConPTY
skeleton) and step 2a (corpus re-recorded on the system ConPTY). The hub does not use the core yet.

| id | decision |
|---|---|
| terminal-core-start | Start the terminal-core work now; no prerequisite load test of Python-side changes. |
| terminal-core-host | The terminal core is a PyO3 extension module (`hub_terminal_core`) inside the hub process, not a sidecar process and not the desktop app. It owns every PTY, parses on its own native threads with the GIL released, and writes the terminal sockets itself, so the hub's event loop is not on the output path. A Rust panic ends one session (archived `crashed`, last screen kept); `abort`, a stack overflow or an access violation still takes the hub down, accepted. |
| terminal-core-ws | The core serves the terminal WebSocket to the console itself, behind a short-lived HMAC ticket the core mints (`GET /api/sessions/{id}/terminal-ticket`), on a `127.0.0.1` ephemeral port. Replay, `replay_end`, Q11 atomicity, A1 resume and W8 keep their current contract. `/mcp`, REST and the console push socket stay in the hub. |
| terminal-core-replaces | The core replaces pywinpty and pyte outright: no `HUB_TERMINAL_CORE` mode, no per-profile switch, no `HUB_TERMINAL_WS` fallback and no Python PTY path kept alongside. Rollback is reverting the merge. pyte survived only as an offline fixture oracle until step 6 deleted it with its renderer and tests. Sessions still end with the hub (`shutdown-ends-cli`). |
| terminal-core-batching | The core's per-session coalescing is the only PTY output batching; the separate Python-side output batching unit is dropped and never lands. |
| terminal-core-conpty | The core uses the system ConPTY through the `windows` crate (`CreatePseudoConsole` / `ResizePseudoConsole` / `ClosePseudoConsole`), not the bundled `conpty.dll` / `OpenConsole.exe` pywinpty ships. Existing captures came from the bundled implementation, so parser fixtures are re-recorded against the system version. |

## Loopback Host/Origin guard (2026-11-14, decided by the orchestrator; the owner approved the master merge)

| id | decision |
|---|---|
| host-guard | Every `http` and `websocket` scope is checked by `LoopbackRequestGuard` (`loopback_request_guard.py`), the app's outermost middleware. Exactly one `Host` is required — `localhost` or a loopback IP, any port, any case; a missing, duplicate, empty or non-loopback `Host` is refused. At most one `Origin` is read: when sent it must be the hub's own page (same transport, loopback name, the very port the request was addressed to) or an entry of `HUB_ALLOWED_ORIGINS`; another loopback port is refused, `null`, an empty `Origin` and a duplicate `Origin` are refused, and no `Origin` passes so MCP clients, the desktop shell and `wait_url` polls are unaffected. `HUB_ALLOWED_HOSTS` / `HUB_ALLOWED_ORIGINS` are parsed with the same parsers as the headers and normalised the same way (`HUB_ALLOWED_HOSTS` entries are `host[:port]`, the port is ignored); `*` is not a wildcard, an unparsable entry is dropped with one start-up warning, and both default to loopback only. Refusals are logged at most one line per normalised `(Host, Origin)` pair per minute and at most 20 lines per minute in total, with one `N refusals not logged` line per window; the line carries the normalised headers, never an unvalidated one or a query string, and the path is `%r`-escaped. |
