## Rust terminal core (2026-11-12, owner: decision page `hub-rust-core-1112`)

Design: `docs/rust-terminal-core.md`. On `feat/rust-terminal-core`: step 0 (frozen corpus), step 1 (ConPTY
skeleton) and step 2a (corpus re-recorded on the system ConPTY). The hub does not use the core yet.

| id | decision |
|---|---|
| terminal-core-start | Start the terminal-core work now; no prerequisite load test of Python-side changes. |
| terminal-core-host | The terminal core is a PyO3 extension module (`hub_terminal_core`) inside the hub process, not a sidecar process and not the desktop app. It owns every PTY, parses on its own native threads with the GIL released, and writes the terminal sockets itself, so the hub's event loop is not on the output path. A Rust panic ends one session (archived `crashed`, last screen kept); `abort`, a stack overflow or an access violation still takes the hub down, accepted. |
| terminal-core-ws | The core serves the terminal WebSocket to the console itself, behind a short-lived HMAC ticket the core mints (`GET /api/sessions/{id}/terminal-ticket`), on a `127.0.0.1` ephemeral port. Replay, `replay_end`, Q11 atomicity, A1 resume and W8 keep their current contract. `/mcp`, REST and the console push socket stay in the hub. |
| terminal-core-replaces | The core replaces pywinpty and pyte outright: no `HUB_TERMINAL_CORE` mode, no per-profile switch, no `HUB_TERMINAL_WS` fallback and no Python PTY path kept alongside. Rollback is reverting the merge. pyte survived only as an offline fixture oracle until step 6 deleted it with its renderer and tests. Sessions still end with the hub (`shutdown-ends-cli`). |
| terminal-core-batching | The core's per-session coalescing is the only PTY output batching; the separate Python-side output batching unit is dropped and never lands. |
| terminal-core-conpty | The core uses the system ConPTY through the `windows` crate (`CreatePseudoConsole` / `ResizePseudoConsole` / `ClosePseudoConsole`), not the bundled `conpty.dll` / `OpenConsole.exe` pywinpty ships. Existing captures came from the bundled implementation, so parser fixtures are re-recorded against the system version. |

## Loopback Host/Origin guard (2026-11-14, decided by the orchestrator; the owner approved the master merge)

| id | decision |
|---|---|
| host-guard | Every `http` and `websocket` scope is checked by `LoopbackRequestGuard` (`loopback_request_guard.py`), the app's outermost middleware. Exactly one `Host` is required — `localhost` or a loopback IP, any port, any case; a missing, duplicate, empty or non-loopback `Host` is refused. At most one `Origin` is read: when sent it must be the hub's own page (same transport, loopback name, the very port the request was addressed to) or an entry of `HUB_ALLOWED_ORIGINS`; another loopback port is refused, `null`, an empty `Origin` and a duplicate `Origin` are refused, and no `Origin` passes so MCP clients, the desktop shell and `wait_url` polls are unaffected. `HUB_ALLOWED_HOSTS` / `HUB_ALLOWED_ORIGINS` are parsed with the same parsers as the headers and normalised the same way (`HUB_ALLOWED_HOSTS` entries are `host[:port]`, the port is ignored); `*` is not a wildcard, an unparsable entry is dropped with one start-up warning, and both default to loopback only. Refusals are logged at most one line per normalised `(Host, Origin)` pair per minute and at most 20 lines per minute in total, with one `N refusals not logged` line per window; the line carries the normalised headers, never an unvalidated one or a query string, and the path is `%r`-escaped. |

## Background persistence (2026-11-10, Hub lock contention fix)

| id | decision |
|---|---|
| buffered-durability | Ordinary telemetry and mailbox success means accepted by the bounded background queue. Forced process termination can lose accepted, uncommitted data. Normal shutdown drains accepted writes; `persisted_in_sqlite` is true only after commit confirmation. |
| sqlite-writer | Keep the existing schema and one Hub per database. Require WAL and `synchronous=FULL`; a dedicated thread owns the only writer, with ordered batches of at most 128 logical units / 25 ms. Lock waits are 100 ms with background retry. |
| bounded-admission | Limit pending writes to 4096 units / 32 MiB. External admission and consistency barriers wait at most 2 seconds before returning temporary unavailability. Internal watchers wait for capacity without advancing their input cursor. |
| oversized-record | (2026-11-13, agent; medium, reversible) A write sized above the whole queue, or above its own reservation, raises `PersistenceRecordTooLarge`, a `PersistenceUnavailable` subclass: retrying it cannot help. `record_telemetry` reduces tool input/output to the stored summaries, clipped details and title before the write is sized, so a multi-MB tool output (a Codex `view_image` result) no longer reaches the estimate. ## Native sub-agent observation (2026-11-10, owner)

Codex delivery revision (2026-11-10, supplemental report): Codex uses bracketed paste with preserved newlines, waits for the complete visible payload or counted literal-prefix-plus-paste-placeholder to settle, then sends at most one Enter. A matching full native user message appended after the write is the only submission proof; screen activity, cleared input and unrelated transcript growth are not proof. An unsettled paste sends no Enter. Failed/unconfirmed drafts block subsequent sends until late native proof or explicit `send_to_subagent(text="", clear_input=true)`; clearing is serialized, requires a visible nonempty idle Codex composer, and confirms removal after one Ctrl+C. Empty sends are no-ops with delivered=false. Replies correlate submit_id, with delivered=true/false/null for confirmed/failed/unconfirmed submissions. Bounded ANSI and terminal dimensions on failures stay under the private data diagnostics directory. Hub-generated failure ANSI is not injected into the native Codex terminal screen. This supersedes flatten-newlines, active-proof and Enter retries for Codex only. Exact cause of the reported old screen drift remains unproven.

Codex paste settle revision (2026-11-13, agent; medium, reversible): a live 915-929-char follow-up failed twice with `typed_text_not_settled`. At 80x24 the composer scrolled (`↑` on its top visible row), so the exact full-text match could never pass; at 144x53 Codex was still taking the paste in a few words per frame at the 10 s cap. The payload now also counts as complete when the composer is scrolled and its visible text is exactly the text's end (>= 40 chars); past the cap the wait continues while the composer keeps changing, until it stands still for 3 s or 120 s have passed. Partial drafts still never get an Enter, and proof is still the native user message only. Parents are told to send long follow-ups as a file plus a one-line pointer. Revert: restore the exact-match line and drop the stall branch in `_await_typed_text_settled`.

Transcript-first principle (2026-11-10, owner): use native transcript records wherever they describe the state. All five supported CLI engines now confirm checked submissions only from a matching full native user message; confirmation never reads screen contents or treats unrelated transcript growth as success. Missing evidence returns unconfirmed without another Enter. Screen inspection remains for draft/composer readiness and native prompts that are not exposed through transcript records. Existing unchecked routes remain explicitly unconfirmed.

DSH workspace permissions (2026-11-10, owner): before local Windows DSH task dispatch or continuation, check the listener process's user SID against the Hub user. On a user-owned workspace with effective WRITE_DAC and missing WRITE_OWNER, automatically add only that host user's non-inheritable WRITE_OWNER ACE on the workspace root. Do not grant FullControl, change ownership/labels, modify ancestors/children, or bypass the sandbox. Pin the directory path with handles, reject reparse/system/root/home paths, serialize by workspace, save a durable private recovery record before mutation, and verify effective rights. On failure remove only the newly added exact ACE from the current DACL, retaining concurrent edits; report rollback failures. Preview and empty re-attachment only check. Remote/unverified hosts skip with a reason; known local preparation failures prevent dispatch. `sandbox_preparation` reports permission preparation, never claims native sandbox startup. No global DSH configuration changes or live-Hub replacement.

Native DSH acceptance limitation: the isolated Modify-only fixture reproduces Win32 5 before repair; root-only WRITE_OWNER lets DSH initialize, read an existing file and create a new file, while outside writes remain denied. The same fixture's pre-existing file does not acquire DSH's capability ACE and remains unwritable by the confined child. Root permission readiness therefore does not guarantee access to existing descendants; repairing those is outside this root-only authorization.
